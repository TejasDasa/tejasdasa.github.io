CUDA Transformer Runtime

A C++/CUDA transformer inference runtime: the full Stories15M forward pass runs on the GPU, matching a CPU reference at every layer, heading toward a paged KV-cache manager and multi-request scheduling.

status
stage 4 of 9: generate text
repo
github.com/TejasDasa/cuda-transformer-runtime

A transformer inference runtime in C++17 and CUDA, targeting compute capability 12.0, running the Stories15M checkpoint. The goal is to build it, understand its execution and memory behavior, then extend it with KV-cache management and scheduling. The distinctive part is measuring how memory layout and execution choices affect inference.

Every operation goes through the same loop: understand it, write a CPU reference, write the CUDA version, compare the results, then measure.

Where it is

Checkpoint loading. A Checkpoint object memory-maps the model file rather than reading it, and owns the mapping for its lifetime. A 7-field header gives the model shape: dimension, hidden dimension, layers, attention heads, KV heads, vocabulary and maximum sequence length. Construction throws on any shape that cannot be a valid model: heads that don’t divide the dimension, more KV heads than attention heads, an odd head size for RoPE. It then computes every weight tensor’s offset into the mapping: embeddings, per-layer attention and FFN weights (wq/wk/wv/wo, w1/w2/w3), RMSNorm weights, RoPE frequency tables and the classifier, which may share the embedding table, and checks that the expected size matches the file byte for byte before anything touches the weights.

The whole model on the GPU. A single-token forward pass runs every layer of Stories15M on the device, from the embedding row to the vocabulary logits:

embedding → for each layer:
              RMSNorm → Q / K / V → RoPE → KV cache → causal attention
              → output projection + residual
              → RMSNorm → W1, W3 → SiLU gate → W2 + residual
          → final RMSNorm → logits

Weights are uploaded once, when the model is built, and stay resident; activations stay on the device from the embedding lookup to the logits, and every kernel runs on the default stream, so each starts only after the one it depends on. Each layer keeps a contiguous K and V cache (one kv_dim row per position), written before attention reads it. Attention is causal over the cached prefix and handles grouped-query attention, with consecutive query heads sharing a KV head. The model tracks its position and accepts only the next one; after a failure part-way through, it refuses to run until it is reset, because the layers’ caches could disagree about the sequence length.

Checked at every step. The CPU reference implements the same model operation by operation. The whole-model test runs a fixed token sequence through both and compares, at every position, the output of every layer, the final normalized vector and every vocabulary logit, within 1e-5 relative plus 1e-5 absolute with NaNs counted as failures. It then resets both models, replays a different sequence, and requires the GPU replay to match the CPU and, bit for bit, a freshly constructed GPU model, which shows reset clears all state. Each kernel also has its own CPU-vs-GPU test, from RMSNorm and RoPE through KV-cache writes and attention.

Against an established implementation. A harness builds Karpathy’s llama2.c run.c at a pinned commit, feeds it the same deterministic token sequence, and compares its logits with this runtime’s at every position. A position passes within 1e-2 absolute with the same top token; the expected agreement is about 1e-4 rather than bitwise, since run.c recomputes the RoPE angles instead of reading the stored tables and accumulates in a different order.

Kernels. Matrix-vector multiply, RMSNorm, RoPE, embedding lookup, KV-cache store, attention scores, softmax, the attention-weighted sum, residual add and the SiLU gate. Attention’s softmax is the numerically stable kind, three passes per row: maximum, exponentials and their sum, then normalization.

__global__ void softmax_rows_kernel(
    float* probs,
    const float* scores,
    int row_stride,
    int active_len
)
{
    __shared__ float partial[kSoftmaxBlock];

    const float* score_row = scores + static_cast<std::size_t>(blockIdx.x) * row_stride;
    float* prob_row = probs + static_cast<std::size_t>(blockIdx.x) * row_stride;

    // (1) maximum.  Threads with no entries contribute -inf, which is the
    // identity for max.
    float local_max = -INFINITY;
    for (int t = threadIdx.x; t < active_len; t += blockDim.x) {
        local_max = fmaxf(local_max, score_row[t]);
    }
    partial[threadIdx.x] = local_max;
    __syncthreads();
    block_max(partial);
    const float row_max = partial[0];
    __syncthreads();   // everyone has read partial[0] before it is reused

    // (2) exponentials.  score - max <= 0, so expf never overflows.
    float local_sum = 0.0f;
    for (int t = threadIdx.x; t < active_len; t += blockDim.x) {
        const float e = expf(score_row[t] - row_max);
        prob_row[t] = e;
        local_sum += e;
    }
    partial[threadIdx.x] = local_sum;
    __syncthreads();
    block_sum(partial);
    const float row_sum = partial[0];

    // (3) normalise.  Each thread touches only the entries it wrote.
    for (int t = threadIdx.x; t < active_len; t += blockDim.x) {
        prob_row[t] /= row_sum;
    }
}

Subtracting the row maximum first keeps every exponent at or below zero, so expf can never overflow however large the scores get.

The KV-cache manager is a cache-design problem in software: allocation granularity, logical-to-physical translation through the block table, locality and capacity, and how that layout interacts with the attention kernels that read it.
