CUDA Transformer Runtime

A C++/CUDA transformer inference runtime, built operator by operator against a CPU reference, heading toward a paged KV-cache manager and multi-request scheduling.

status
stage 3 of 9: one transformer layer
repo
github.com/TejasDasa/cuda-transformer-runtime

A transformer inference runtime in C++17 and CUDA, targeting compute capability 12.0, running the Stories15M checkpoint. The goal is to build it, understand its execution and memory behavior, then extend it with KV-cache management and scheduling. The distinctive part is measuring how memory layout and execution choices affect inference.

Every operation goes through the same loop: understand it, write a CPU reference, write the CUDA version, compare the results, then measure.

Where it is

Checkpoint loading. A Checkpoint object memory-maps the model file rather than reading it, and owns the mapping for its lifetime. A 7-field header gives the model shape: dimension, hidden dimension, layers, attention heads, KV heads, vocabulary and maximum sequence length. Construction throws on any shape that cannot be a valid model: heads that don’t divide the dimension, more KV heads than attention heads, an odd head size for RoPE. It then computes every weight tensor’s offset into the mapping: embeddings, per-layer attention and FFN weights (wq/wk/wv/wo, w1/w2/w3), RMSNorm weights, RoPE frequency tables and the classifier, which may share the embedding table, and checks that the expected size matches the file byte for byte before anything touches the weights.

Layer 0 on the GPU. The first slice of a transformer layer runs end to end on the real Stories15M weights and is checked against the CPU at every step:

token embedding → attention RMSNorm → Q / K / V projections → RoPE on Q and K

Q and K stay resident on the device between the projections and RoPE; only the results come back for comparison. Every intermediate (the normalized input, Q, K, V, and rotated Q and K) matches the CPU reference within 1e-5 relative plus 1e-5 absolute, with NaNs counted as failures. RoPE is applied at positions 0, 1, 7 and the last position, since position 0 is the identity rotation and proves nothing on its own. V is checked unchanged after each rotation, the checkpoint’s cos/sin tables are checked against the RoPE formula at every position, and out-of-range positions are rejected before a table row is read. Device memory is owned by a small RAII DeviceBuffer, so every allocation is freed on any exit path, including a failed check.

Kernels. RMSNorm, matrix-vector multiply and RoPE, each with a CPU twin and its own test. RoPE rotates each head’s adjacent pairs by an angle that grows with position, one thread per pair:

__global__ void rope_kernel(float* vec, int n_heads, int head_size, const float* cos_row, const float* sin_row)
{
    const int pairs_per_head = head_size / 2;
    const int total_pairs = n_heads * pairs_per_head;

    const int t = blockIdx.x * blockDim.x + threadIdx.x;
    if (t >= total_pairs) {
        return;   // the last block is usually only partly filled
    }

    const int head = t / pairs_per_head;
    const int pair = t % pairs_per_head;
    const int base = head * head_size + 2 * pair;

    const float c = cos_row[pair];
    const float s = sin_row[pair];

    const float a = vec[base];
    const float b = vec[base + 1];

    vec[base]     = a * c - b * s;
    vec[base + 1] = a * s + b * c;
}

Each thread owns both elements of its pair, so reading both and writing both back is race-free even though the update is in place.

The KV-cache manager is a cache-design problem in software: allocation granularity, logical-to-physical translation through the block table, locality and capacity, and how that layout interacts with the attention kernels that read it.
