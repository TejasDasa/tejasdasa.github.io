Protocol Emulator ASIC

Five programmable state machines on a Tiny Tapeout 6×4 die in IHP 130nm, bit-banging UART, SPI, I²C, USB low-speed, JTAG and CAN from 32-row programs.

status
signed off · Tiny Tapeout submission pending
competition

repo
github.com/TejasDasa/protocol-emulator-asic

An open-source protocol emulator, built as an entry to the Jane Street ASIC design competition. Five independent state machines drive and read pins directly. Each executes one 32-bit row per clock, with no pipeline, no stalls and no skipped cycles, so protocol timing is something you read off the program rather than count and hope about. Programs load at run time over serial chains, so the silicon is not committed to any protocol at tape-out.
ProcessIHP SG13CMOS5L 130nm, via Tiny Tapeout
Area6 × 4 tiles, 59.3% instance utilization
Machines5, each with two CFGMEM_IHP16 instruction-memory macros
Row32 bits, one per clock; at most 32 rows per program

Signoff0 DRC (Magic, KLayout, router), 0 LVS, 0 antenna, 0.02% worst IR drop
Timing−2.20 ns setup at the slow corner, so ~45 MHz against a 50 MHz target

One row, one clock

A row says one thing: when this test passes, do these actions, then go there. There is no implicit fall-through. Every row carries its own successor, which is what lets a single self-looping row be a precise wait.

bitsfield
[3:0]testtimer, two counters, a shift-register bit, input pins, FIFO status
[5:4]modederives both the true and false exits from one target
[13:6]targetrow index, or 255 to return through the link register
[15:14]pin_slotoutput slot; 3 selects the D+/D− pair
[18:16]pin_opoperation on that slot
[31:19]actionsfive mutually exclusive groups: shift register, counter 1, counter 2, timer, CRC/call

UART TX is five rows (step it in the simulator):

SttProgram([
    Row("IDLE",  "fifo", "START", pins={0: "lo"}, act=["load", "cload", "trst"]),
    Row("START", "tmr",  "DATA",  pins={0: "sr"}),
    Row("DATA",  "tmr",  "CHECK", pins={0: "sr"}, act=["shift", "cdec"]),
    Row("CHECK", "cz",   "STOP",  "DATA"),
    Row("STOP",  "tmr",  "IDLE"),
])

The encoding is generated, not transcribed: the specification’s tables and the RTL’s decode constants both come from one isa.json, checked against the Python models, so drift between spec, model and RTL is a build failure.

Why a state table

The architecture came out of a Python ISA benchmark study. Three candidates, each with cycle-accurate models, the same host interface, and five protocol programs checked by independent device models:

UART TX64140224225
UART RX144224256235

PIO is RP2040-style, 16-bit instructions. RM is a 32-opcode register machine. *PIO cannot compute CRC5, so its host supplies a prebuilt word.

The state table matches PIO on cycles per bit and beats the register machine on both axes. It does not win on program bits: PIO is smaller on four of five. So the case against PIO is not “better”, but a different set of trades, each one measured, with the costs stated as precisely as the benefits.

Where it improves on PIO

  • Per-machine instruction memory. PIO shares 32 instructions across four state machines. Here each of five machines has its own 32 rows, so a 25-row JTAG program doesn’t starve anything else.
  • A branch in every row. No implicit fall-through; every row names both exits. “Wait until” is one self-looping row, not a compare-and-jump sequence.
  • Inline actions. 13 bits reach 1,800 action sets, against PIO’s eight instruction types, and there are no slots to run out of after fabrication. The rejected palette format had 8 loadable entries, and USB alone used 7.
  • On-chip CRC and bit stuffing. PIO has neither. In the study, PIO’s USB host had to compute CRC5. CAN is the harder case: 54 rows in software against a 32-row ceiling, 24 with the units.

Where it is behind

  • No autopush/autopull. PIO moves data between shift register and FIFO automatically; here each move costs a row.
  • No side-set. PIO writes a pin alongside another action. One pin write per row is why JTAG, which walks TMS, TDI and TCK, costs 25 rows.
  • No CPU beside it. PIO has no inter-machine signalling either, but it sits next to two Cortex-M0s that do the framing. This chip has no CPU, and the ISA cannot turn a test result into data, a structural limit with three measured costs: CAN destuffing, USB NRZI decode, and USB receive bit rate.
  • No DMA. PIO’s FIFOs are DMA endpoints. These are four entries deep, behind a serial host port.

Not comparable

PIO has shipped in millions of parts and has had every protocol people have invented thrown at it for five years. This design has seven protocols against its own models, three validated on an FPGA, and none in silicon. Its three structural limits were found by trying to falsify the design, not by a reviewer.

The row format was then chosen by synthesis, not estimate. A 21-bit row with a 32-entry action palette against a 32-bit row with actions inline: under CFGMEM a row bit costs 79 µm² against 2,618 µm² in flops, so the wider row’s extra program bits are close to free while the palette hardware it removes is not. The 32-bit format is also a strict superset, which matters for a chip whose point is protocols chosen after fabrication.

The 32-row ceiling

No stall means a program either fits in 32 rows or does not exist.

programrows
UART detector: decides what a wire is carrying12
USB LS receive24
CAN 2.0A transmit, with the per-machine CRC and bit stuffer24
JTAG25
CAN 2.0A without those units54: does not exist

CAN is the case for the two wider units, and it is an impossibility argument rather than a cost one. CAN stuffs after five identical bits, and no test in the ISA reports the previous bit, so a software stuffer has to fork the program by polarity and unroll the run length: 54 rows. Worse, in the CRC field the bit comes out of the CRC register and no test reads it, so no row count would be enough. With the units, the same frame is 24 rows, for +53 flops per machine.

The same no-stall rule forces those units to be per machine: a shared resource reachable by several rows on one cycle needs arbitration, arbitration means a machine waits, and there is nowhere for the wait to go.

Verification

  • Cycle-exact lockstep. RTL and Python models step together, compared every cycle on every architectural register, FIFO operation and pin.
  • Mutation. 350 single-point program mutants; 89.1% killed, gated at 85% and at the mutant count so a removed benchmark fails the build.
  • Random programs. Generated 32-row programs reaching decode paths no hand-written protocol exercises.
  • Formal. Five properties proved over the whole input space with SymbiYosys, each shipped with a deliberate break that must fail. It found three regions the specification left undefined.
  • Gate level. SDF back-annotated simulation of the signed-off netlist: worst inter-pin skew 0.707 ns at the slow corner.
  • FPGA. On a Cora Z7-07S: UART TX into a CP2102 at 9600 baud, UART TX→RX and USB LS token TX→RX across two machines, through real pads.

What is not validated is recorded as carefully: SPI, I²C and CAN have only run against models written in this repo; hardware runs are two machines, not five; USB is configured at 1.5625 Mbit/s, 4.17% off the standard’s 1.5; and the design has not yet been submitted to Tiny Tapeout, so nothing has run in silicon.

Physical design

The load-bearing physical constraint was grid alignment. A macro’s power pin columns, not its origin, must land on the power-stripe grid. Off by 2.88 µm, the stripes over the macros get no vias and the entire power network is sourceless: IR-drop analysis cannot run and LVS fails. Six machines were ruled out by measurement, not projection: global routing overflows by 2,846 GCells, because macros block three of four metal layers beneath them.
